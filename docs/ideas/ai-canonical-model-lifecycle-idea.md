# IDEA: AI-Driven Canonical Model Lifecycle — Generate, Maintain, Monitor

## Status
Draft product thesis.

## Central Idea

> The canonical model is the structural contract that makes AI-driven generation, maintenance, and monitoring meaningful rather than noisy.

GuideRail's canonical grammar — domains, capabilities, journeys, processes, architecture, systems, sequences, control points — defines a target shape that AI can:

1. **Generate** from existing organizational assets
2. **Maintain** by watching source-of-truth systems for drift
3. **Monitor** by comparing runtime behavior against the declared model

The grammar is what makes all three possible. Without a defined schema for what a "capability" is, how it links to a "process," and how a "control point" governs a "stage," AI has nothing to map into, nothing to reconcile against, and nothing to monitor for.

---

## The Problem Today

Every organization already has a canonical model. It's scattered across:

- Architecture diagrams in ArchiMate or Visio
- Process flows in Camunda or Bizagi
- Journey maps in Miro or Figma
- Service catalogs in Backstage or ServiceNow
- API specs in OpenAPI or Postman
- Control frameworks in spreadsheets or GRC tools
- Context and rationale in Confluence, wikis, and people's heads

The traceability exists implicitly — someone knows that the "Payment Authorization" capability maps to a user journey, which maps to a BPMN process, which maps to services, which map to API calls. But:

- **It's not unified.** Each tool owns a slice. Nobody can trace a thread from capability to runtime call sequence without hopping between 5 tools.
- **It's not linked.** The same concept appears in multiple tools under different names with no programmatic connection.
- **It decays.** When code changes, diagrams don't update. When APIs change, sequence diagrams are already stale. Drift is inevitable.
- **Nobody maintains the whole picture.** Each team is responsible for their part, not how it all connects. The cross-perspective linkage rots because no single person or team owns it.

---

## Why AI Changes This

AI dissolves the ownership problem. It doesn't care about org boundaries. It can read:

- The architecture team's ArchiMate model
- The product team's journey maps
- The platform team's service catalog
- The compliance team's control framework
- The engineering team's codebase and API specs

And produce one unified canonical model that links them all — with stable IDs, explicit foreign keys, provenance tracking, and cross-perspective continuity.

The canonical grammar is the target shape. AI is the mapping engine. Runtime is the validation surface.

---

## The Three-Phase Lifecycle

### Phase 1: AI Generates the Model

Point AI at existing organizational assets and it produces the canonical model through ingestion mapping.

**Input sources:**
- Codebase (file structure, imports, module boundaries → architecture nodes and edges)
- API specifications (OpenAPI/Swagger → interfaces, messages, sequences)
- BPMN files (Camunda exports → processes, stages, gateways)
- Architecture models (ArchiMate → domains, capabilities, architecture nodes)
- Service catalogs (Backstage → system participants, deployment metadata)
- Control frameworks (GRC exports → control points with severity, regulatory refs)
- Documentation (wikis, READMEs → journey narratives, capability descriptions)

**Output:**
- Canonical model entities with stable IDs
- Foreign keys linking entities across perspectives
- Provenance refs tracking which source artifact produced each entity
- A traversable corpus ready for GuideRail

**What AI does that humans won't:**
- Reads across organizational boundaries without politics
- Identifies the same concept appearing under different names in different tools
- Produces the cross-perspective linkage that no single team maintains
- Generates the full entity graph in hours, not months

This is not hypothetical. In this codebase, the self-referential corpus was generated by AI reading the actual code and producing domains, capabilities, processes, sequences, architecture nodes, and edges with correct foreign keys. The same approach works against any codebase or artifact set.

### Phase 2: AI Maintains the Model

The canonical model is not a one-time artifact. It must stay current as the organization evolves. AI watches source-of-truth systems and reconciles the model against observed changes.

**Triggers:**
- A PR adds a new service → AI flags: "this service isn't in the architecture perspective; 2 sequences reference its API but the canonical model doesn't include it as a participant"
- An API contract changes → AI flags: "message 7 in the payment authorization sequence references a field that no longer exists in the API spec"
- A BPMN process is updated → AI flags: "stage 3 was removed but the canonical model still references it; 1 control point is now orphaned"
- A new regulatory requirement arrives → AI flags: "3 capabilities have no control points for this regulation"

**What AI does that humans won't:**
- Continuously monitors all source systems, not just the one the team happens to own
- Detects cross-perspective impact (a code change affecting a process affecting a control point)
- Produces model update proposals with provenance: "I updated this entity because this source artifact changed"
- Prevents the decay that makes every hand-maintained model eventually stale

### Phase 3: AI Monitors Against the Model

The canonical model becomes the expected-state contract. Runtime telemetry is the observed state. AI reports the delta.

**What AI can monitor:**

- **Sequence violations** — "the fraud check was skipped at runtime, but the canonical model declares it as mandatory at stage 3 of the payment authorization process"
- **Control drift** — "control point CP-PCI-AUTH is declared as compliant with severity: high, but the runtime behavior shows the encryption step is bypassed in 2% of requests"
- **Architecture divergence** — "a new service appeared in the API call chain that isn't declared in the canonical model; it's receiving sensitive data but has no control points"
- **Process deviation** — "the declared process has 8 stages in order; the observed execution skips stage 4 and reverses stages 6 and 7 in 15% of cases"
- **Capability health** — "3 of 5 processes under the Payment Processing capability are showing anomalies; the capability's effective health score has dropped"

**What makes this different from existing APM/observability:**

Existing monitoring tools (Datadog, New Relic, PagerDuty) watch infrastructure metrics — latency, error rates, CPU, memory. They know *that* something failed. They don't know *what it means*.

The canonical model gives AI **semantic context**:

- It doesn't just know an API call failed — it knows the call is part of a payment authorization sequence, governed by a PCI control point, under a capability that 2 user journeys depend on
- It doesn't just know latency increased — it knows which process stage is slow, which capability is affected, and which control points are at risk
- It doesn't just alert on errors — it alerts on **model violations**, which are categorically more meaningful than threshold breaches

## The Control Point Connection

Control points are where this thesis becomes critically valuable. The canonical grammar already defines:

| Field | What it provides to AI monitoring |
|---|---|
| `severity` | Priority ranking for alerts — high-severity violations escalate immediately |
| `controlType` | Classification of what kind of control (authorization, validation, encryption, audit) |
| `status` | Declared compliance state — AI can compare declared vs observed |
| `regulatoryRef` | Which regulation requires this control — ties violations to compliance risk |
| `processStageId` | Where in the process this control applies — AI knows exactly which step to watch |

An AI monitoring system with access to this grammar can produce alerts like:

> "Control CP-PCI-AUTH (severity: high, regulation: PCI-DSS 3.2.1) requires encryption at process stage 3 (Network Authorization) of the Payment Authorization process. Runtime telemetry shows 847 requests in the last hour bypassed the encryption step via the legacy API path. This affects the Payment Processing capability, which is exercised by 2 user journeys. Recommended action: block the legacy path or update the control point status to non-compliant."

That alert contains business context, regulatory context, architectural context, and remediation guidance — all derived from the canonical model.

## Why the Grammar Must Come First

AI can generate monitoring rules from logs. AI can detect anomalies from metrics. AI can even infer service dependencies from traffic patterns.

But without the canonical grammar, AI cannot:

- Know which anomalies matter to which business capabilities
- Connect a runtime failure to a regulatory control obligation
- Trace a process deviation back to the user journey it affects
- Distinguish an intentional architecture change from unauthorized drift
- Produce alerts with semantic meaning rather than statistical noise

The grammar is the **interpretive layer** between raw observability data and meaningful operational intelligence. It's what turns "service X returned 500" into "the fraud screening control in the payment authorization process failed, putting PCI compliance at risk for the Customer Onboarding capability."

## The Ownership Problem — Solved

The historical blocker for canonical models is ownership:

- Architecture team maintains architecture diagrams
- Product team maintains journey maps
- Platform team maintains service catalogs
- Compliance team maintains control frameworks
- Nobody maintains the linkage between them

AI solves this in two ways:

1. **Initial generation requires no cross-team coordination.** AI reads all the artifacts independently and produces the linked model. No meetings, no alignment sessions, no "who owns the canonical model" debates.

2. **Ongoing maintenance is automated.** AI watches all source systems continuously. When any team's artifacts change, AI reconciles the canonical model and proposes updates. The model stays current without anyone being "responsible" for the whole thing.

The org doesn't need a new role or a new process. It needs a grammar (the canonical model schema) and an AI system that maps into it, maintains it, and monitors against it.

## Implementation Path

### Near-term (GuideRail 0.8.0–1.0)
- **Ingestion mapping from files** — `parseContentBundle()` already validates JSON through Zod schemas. Extend to accept ArchiMate XML, OpenAPI YAML, BPMN XML, and produce canonical entities.
- **AI-assisted generation** — given a codebase or artifact set, prompt an LLM to produce the canonical model. The grammar (entity schemas, foreign key relationships, perspective bindings) provides the structured output format.
- **Provenance tracking** — already in the schema. Every generated entity carries a ProvenanceRef back to its source artifact.

### Medium-term (GuideRail 1.x)
- **Continuous reconciliation** — watch source systems (git repos, API registries, BPMN engines) for changes. When a source artifact changes, re-run ingestion mapping for affected entities and flag drift.
- **Model diff and review** — show what changed in the canonical model and why, with provenance links. Teams review model updates like code reviews.

### Long-term (GuideRail 2.x)
- **Runtime monitoring integration** — connect to observability platforms (OpenTelemetry, Datadog, etc.). Compare observed call sequences against canonical sequences. Compare control point declared status against observed behavior.
- **Automated alerting** — alerts enriched with canonical model context: which capability, which control point, which regulation, which user journey is affected.
- **Health scoring** — aggregate signals across all perspectives for each capability. Surface capabilities at risk before incidents occur.

## Strategic Positioning

This thesis positions GuideRail as three things:

1. **A modeling discipline** — the canonical grammar that teaches organizations how to think about cross-perspective traceability
2. **A visualization tool** — the guided traversal experience that makes the model navigable and teachable
3. **An operational intelligence substrate** — the structural contract that makes AI-driven generation, maintenance, and monitoring meaningful

The grammar is the foundation. The tool rewards the discipline. AI operationalizes both.

---

## Closing

The canonical model has always been valuable. The problem was always maintenance — nobody owns the whole picture, so the linkage decays.

AI dissolves that problem at every stage:

- **Generation:** AI reads existing artifacts across organizational boundaries and produces the linked model
- **Maintenance:** AI watches source systems and reconciles the model continuously
- **Monitoring:** AI compares runtime behavior against the declared model and produces semantically meaningful alerts

The canonical grammar is what makes all three possible. Without it, AI is just another monitoring tool producing noise. With it, AI becomes an operational intelligence system that understands what the organization is supposed to do, how it's supposed to work, and when reality diverges from intent.

That is the product thesis: **GuideRail's canonical model is the contract between organizational intent and operational reality, and AI is the enforcement mechanism.**
